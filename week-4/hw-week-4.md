# Домашка - Неделя 4

## 1) ADR по изменению коммуникации

### ADR-001: Убираем задержку рейтинга между Hiring и Bonuses

**Status:** Proposed

**Context**

Рассматриваем `COMM-060`: передача `TaskRating` из `Hiring` в `Bonuses`.
У нас есть бизнес-процесс: начисление бонусов менеджеру после проверки задания. Проблема заключается в том, что
асинхронная передача рейтинга давала eventual consistency, из-за чего в момент начисления бонусов использовался
неактуальный рейтинг.
Ограничения: не меняем границы 3 сервисов.

**Decision**

- В `Bonuses` добавить endpoint обновления актуального рейтинга в операции начисления.
- Перевести `COMM-060` из асинхронного события в синхронный.
- Продьюсер `TaskRating` выключить после переключения типа коммуникации.
- Синхронным вызовом в этом месте даём требуемую strong consistency для расчёта бонусов менеджеру.

**Consequences**

- Плюсы:
    - Закрываем `Problem-030`: рейтинг на момент начисления актуален.
    - Упрощается коммуникация (один синхронный вызов проще продьюсинга/консьюминга).
- Минусы и риски:
    - Выше связность между `Hiring` и `Bonuses`.
    - Влияние недоступности `Bonuses` на логику проверки заданий.
    - Увеличим длительность логики проверки заданий

**Compliance**

- FF-1 (atomic/triggered/automated/threshold): в CI интеграционный тест подтверждает, что начисление берёт актуальный
  рейтинг из текущего вызова.
- FF-2 (atomic/continuous/automated/threshold): p95 latency вызова Hiring -> Bonuses не превышает согласованный порог.
- FF-3 (atomic/continuous/automated/threshold): доля кейсов начисления по неактуальному рейтингу равна 0.

**Alternatives**

- Оставить async + ретраи: решает доставку, но не решает strong consistency.
- Также рассматривался вариант с pull-ом рейтинга из `Hiring` во время выплат бонусов менеджерам, но так сложнее понять,
  какой рейтинг был использован в момент каждой операции

## 3) Fitness-функции для Scalability и Reliability

### 3.1 Scalability

- atomic - проверяем один сервис: `RPS`, `p95 latency`, `CPU/memory`.
- holistic - делаем сквозной нагрузочный тест всей системы.
- automated - включаем алерты на рост `queue lag`, `5xx`, saturation.
- manual - вручную запускаем стресс-тест перед крупными релизами.
- triggered - запускаем нагрузочный прогон после каждого релиза.
- continuous - постоянно мониторим "золотые сигналы" и async-метрики.
- trend - смотрим тренд `p95 latency` и `queue lag` по релизным циклам.
- threshold - фиксируем порог: система выдерживает `500 учителей + 5000 кандидатов`.

### 3.2 Reliability

- atomic - контролируем один критичный набор связей (`COMM-040`, `COMM-050` `COMM-060`): ошибки, дубли, retry.
- holistic - проверяем ключевой флоу целиком: "сдача задания -> начисление бонуса".
- automated - ставим алерты на `error-rate`, failed connections, рост `Retry-Topic`, `DLQ`.
- manual - проводим ручной `disaster recovery/rollback drill`.
- triggered - после релиза запускаем failure drill на stage стендах.
- continuous - постоянно собираем метрики и логи по отказам.
- trend - отслеживаем тренд `MTTR` и повторных инцидентов.
- threshold - держим `SLA >= 99.9%` по доступности.

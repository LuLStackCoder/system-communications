## 2. Миграция четырёх связей (3.2)

### 2.1 Переход формальной sync -> async (event-driven)

Запрос информации о кандидатах в учителя (`[COMM-090]`, синхронный) меняем на стриминг кандидатов (из «Найм» в «Задания»).

1. Добавляем схему формального события о кандидате (`Candidate.Created/Updated/Deleted`) в schema registry.
2. Пишем консьюмера в сервисе «Задания» (upsert в read model + обработка дублирования по `event_id`).
3. Пишем продьюсера в сервисе «Найм».
4. Переключаем сервис «Задания» на использование локальной read model вместо синхронного запроса.
5. Если всё ок, удаляем синхронный код и чистим хвосты в обоих сервисах (клиент, метрики, документация).

### 2.2 Переход формальной async -> sync

Асинхронное событие обновления рейтинга из «Найма» в «Бонусы» (`[COMM-060]`) меняем на синхронный вызов (нужно для сильной консистентности на момент начисления).

Вариант: push-стратегия через HTTP.

1. В «Бонусах» добавляем эндпоинт для обновления рейтинга задания (например, `POST /api/task/{id}/rating/update`).
2. В «Найме» отключаем продьюсер и переходим на синхронный вызов этого эндпоинта.
3. В «Бонусах» мониторим, что старые события закончились, после чего удаляем консьюмера.
4. Подчищаем хвосты в обоих сервисах (код/топики/метрики/доки).

### 2.3 Переход функциональной sync -> async (event-driven)

Синхронный вызов назначения менеджера на переделку задания (из «Найма» в «Задания») меняем на функциональное событие «задание выполнено правильно».

1. Добавляем схему функционального события о правильном выполнении задания в schema registry.
2. Добавляем в сервис «Задания» пустого консьюмера (пока без бизнес-логики) и проверяем доставку.
3. Пишем продьюсера в сервисе «Найм» (генерирует события о корректном выполнении задания).
4. Проверяем, что всё работает.
5. Переносим бизнес-логику назначения/поиска менеджера в консьюмер «Заданий».
6. Подчищаем хвосты: удаляем синхронный код и всё, что больше не используется.

### 2.4 Переход функциональной async -> sync

В текущей системе нет подходящей связи такого типа, поэтому миграцию пропускаю.

## 4. Как не потерять деньги (начисления и списания)

1. Outbox в «Найме» для событий `Task.Completed/Task.Failed`.
   - Зачем: чтобы не было состояния “в БД зафиксировали результат, а событие в брокер не ушло”.
   - Ошибки: если публикация в брокер упала, воркер ретраит по outbox до успеха.

2. Ack + ретраи на продьюсере.
   - Зачем: брокер/сеть временно недоступны.
   - Ошибки: ретраи с backoff, алерт на рост ошибок/размер outbox.

3. Idempotency в «Бонусах» по `event_id`.
   - Зачем: при `at-least-once` событие может прийти повторно.
   - Ошибки: повторное событие не меняет баланс, только логируется.

4. Retry topic + DLQ для ошибок обработки событий.
   - Зачем: разделить временные ошибки (можно повторить позже) и перманентные (невалидная схема/данные), чтобы не стопорить консьюмера.
   - Ошибки: при временной ошибке перекидываем событие в retry topic (с backoff и счётчиком попыток); при исчерпании попыток или при невалидности отправляем в DLQ с причиной; после фикса делаем replay.

5. Ledger по операциям (`BalanceOperation`) вместо “перезаписи баланса”.
   - Зачем: аудит и восстановление баланса при спорных ситуациях.
   - Ошибки: баланс всегда можно пересчитать из операций, а проблемные операции найти по `event_id`.

6. Реконсиляция.
   - Зачем: ловить расхождения и “тихие” потери.
   - Ошибки: регулярная сверка суммы операций с агрегированным балансом + алерты на расхождения.
